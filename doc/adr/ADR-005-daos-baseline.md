# ADR-005: DAOS 본체 기준선 — 상류 RPM 을 쓰고, 사내 확장판은 보류

- 상태: **승인**(2026-10-08, kpkim) — 1~3 은 현재 운영 그대로, 4(두 판 운영)는 **보류**(2026-10-07, kpkim)
- 날짜: 2026-10-07
- 결정자:

## 배경

- **지금 K8s 제품은 상류 DAOS 2.8 을 그대로 쓴다.** daos-images 가 `packages.daos.io` v2.8 저장소에서
  `daos-server-2.8.0-6.el9` 등을 설치한다(Packager: DAOS Foundation). 2026-10-06 CI 레인 A 서버 파드에서
  확인했다. 사내 저장소 exastor/daos 의 코드는 들어 있지 않다.
- **exastor/daos `base/2.8`** 은 상류 `v2.8.0` 위에 기능 커밋 13개를 얹었다.

  | 확장 | 커밋 | 건드리는 층 |
  |---|---|---|
  | POSIX ACL(setfacl, mask 동기화) | a207012f, ecac88ad, 5b1c3923 | 클라이언트(dfuse) |
  | statfs 를 쿼터 기준으로 | c07f2e50 | 클라이언트(dfuse) |
  | `dfs_open_by_oid` | 8ed2f294 | 클라이언트(libdfs) |
  | 컨테이너 하드 쿼터·사용량 회계·EC 보정 | e71a8b4f, 167adbeb, 564c5d7f, dca4651e, 3e5350a3 | 서버(VOS·컨테이너) + 프로토콜 |
  | 프로젝트 쿼터(Lustre projid) | e375f0f9 | 서버 디스크 형식 |
  | 버그 수정(VOS 크래시, bdev scan, cont_prop rc) | c29d582b, 29943605, b3331077 | 서버 |

- 상류는 쿼터·ACL 같은 POSIX 호환 기능에 대응이 느리다. 이 기능들은 엔터프라이즈 판매 근거가 될 수 있다.
- 반면 DAOS 3.0 은 하위 호환 없는 프로토콜 변경을 예고했고(ADR-003), 팀은 3명 규모다.

## 결정

1. **K8s 제품의 DAOS 본체 기준선은 상류 공식 RPM 이다.** 우리 차별점은 DAOS 바깥(operator, CSI,
   KV 캐시 커넥터, S3 게이트웨이)에 둔다.
2. **사내 패치는 예외로만 얹는다.** 아래를 모두 만족할 때만 허용한다.
   - 고객 출하나 PoC 를 실제로 막는 결함이다.
   - 상류 PR 을 먼저 내고 그 링크를 패치에 붙인다.
   - "상류 병합 또는 다음 상류 릴리스에서 제거"를 기한으로 둔다.
   - 이미지 태그로 상류 그대로인 빌드와 구분한다.
3. **결함은 가능하면 DAOS 바깥에서 고친다.** 2026-10 기준 K8s 제품에 필요했던 DAOS 쪽 문제는 모두 본체 패치 없이 풀렸다.

   | 문제 | 해결 위치 |
   |---|---|
   | S3 multipart 쓰기 시 엔진 SIGSEGV | versitygw 포크 |
   | 엔진 기동 Segfault(설계 §13 #24) | 이미지의 libfabric 을 DAOS 저장소 1.22.0 으로 고정 |
   | 준비 전 사망한 엔진을 daos_server 가 놓침 | operator 가 엔진 재기동·파드 재시작(!27), 상류 보고 대상 |

4. **두 판 운영(상류 기본판 + exastor 확장판)은 보류한다.** 진행하게 되면 아래 "보류된 설계"를 출발점으로 삼는다.

## 보류된 설계: 두 판 운영

### 판 구성
| | 기본판 | 확장판 |
|---|---|---|
| 서버 | 상류 RPM | exastor RPM(쿼터 포함) |
| 클라이언트 | 상류 RPM. 클라이언트에서 끝나는 확장(ACL)은 우리 이미지에 넣을 수 있다 | exastor RPM |
| 대상 | 공개 차트, 커뮤니티 | 엔터프라이즈 구독, FlexA |

### 운영 원칙
- **판은 세트로 전환한다.** 한 시스템 안에서 서버와 모든 클라이언트 이미지(agent, client, CSI, versitygw-daos,
  vllm-lmcache-daos)를 같은 판으로 맞춘다. 서로 다른 판을 섞지 않는다.
  고객이 직접 빌드한 애플리케이션은 확장판에서 우리 클라이언트 RPM 을 쓰는 것을 지원 조건으로 둔다.
- **전환은 기본판 → 확장판 일방향이다.**
  - 상류가 만든 풀은 쿼터 속성이 없어 기본값(무제한)으로 읽히고, VOS 예약 영역이 0 이라 프로젝트 쿼터 트리도 비어 있는 것으로 처리된다.
  - 반대 방향은 상류가 모르는 속성과 예약 영역 사용 때문에 이관이 필요하다. 고객에게 미리 알린다.
- **전환은 전체 중단 방식이다**(ADR-003). 클라이언트 워크로드 파드의 재시작은 운영 절차로 안내한다.
- **판을 표식으로 구분한다.** 이미지 태그에 판을 넣고, operator 는 서버 판을 감지한 뒤에만 확장 기능 필드(쿼터 등)를 받는다. CRD 는 하나로 유지한다.
- **확장판은 상류 태그 위로 매번 rebase 한다.** 패치마다 "상류에 낼 것"과 "제품 전용"을 표시한다.
  쿼터·ACL 은 상류에도 비어 있는 기능이라 상류 제안을 병행한다.

### CI 와 배포 구조
1차는 상류판, 2차로 확장판을 더하는 순서를 전제로 한다. CI 와 차트는 하나로 두고 판(edition)을 변수로 고른다.

**CI**
| 위치 | 지금 | 확장판을 더하는 방법 |
|---|---|---|
| daos-images | `Dockerfile.base` 의 `ARG DAOS_REPO_URL`(packages.daos.io) | 같은 Dockerfile 을 확장판 RPM 저장소(ac2repo) URL 로 한 번 더 빌드한다. 태그에 판을 붙인다(예: `2.8.0-YYYYMMDD-gSHA-ext`) |
| operator CI | `DAOS_IMAGE_TAG`, 프로파일의 이미지 태그 | e2e 를 판 변수(`EDITION`)로 실행하고 `E2E_SET` 으로 이미지 태그만 바꾼다 |
| e2e 시험 | 공통 시험 | 공통 시험은 두 판 모두 통과해야 한다. 확장판 전용 기능(쿼터 등)은 라벨(예: `ext`)을 붙여 확장판에서만 돈다 |

- MR 게이트(e2e-tier1)는 상류판만 돌린다(레인 B, 지금 속도 유지).
- 야간은 판마다 따로 돌린다(예: 상류판 01:00, 확장판 03:00, 각각 레인 A 약 2시간). 레인이 모자라면 격일로 번갈아 돌린다.
- 확장판 RPM 은 exa-build 에서 빌드한다(RPM 빌드는 되고, 2.8 바이너리를 실행하지 못하는 것은 이미지 빌드에 영향이 없다).
- **DAOS 클라이언트가 들어간 이미지는 모두 판별로 만든다**: agent, client, admin, CSI(dfuse), versitygw-daos,
  vllm-lmcache-daos. 서버만 바꾸면 위 "판은 세트로 전환한다"가 깨진다.
- 확장판 RPM 저장소에도 libfabric 1.22.0 이 있거나 DAOS 저장소를 함께 붙여야 한다. 이미지 빌드는 1.22.0 이 아니면 실패한다(daos-images !3).
- 이미지 빌드와 야간 e2e 가 두 배가 된다. exa-build 디스크(2026-10-06 99%)와 레지스트리 rate limit 이 더 빨리 다시 찾아온다.

**Helm 차트**: 이름을 나누지 않는다.
| 방식 | 판단 |
|---|---|
| 같은 차트 이름, values `edition: upstream \| extended` 로 operator·CSI·DAOS 이미지 태그를 세트로 고른다. 확장판 설정은 `editions/extended-values.yaml` 같은 파일로 준다 | **채택** |
| 같은 이름을 배포처만 나눈다: 상류판은 `oci://ghcr.io/gluesys/charts/daos-operator`(Artifact Hub), 확장판은 비공개 레지스트리 | 위와 함께 쓴다 |
| 다른 차트 이름(`daos-operator-enterprise` 등) | 라이선스·판매 조건이 완전히 갈릴 때만 |

- **CRD 는 하나여야 한다.** 이름이 다른 두 차트가 같은 CRD(`daossystems.daos.gluesys.com`)를 설치하면 한 클러스터에서
  서로 덮어쓴다. 확장판 전용 필드는 같은 CRD 의 선택 필드로 두고, operator 가 서버 판을 감지해 상류판이면 거부한다.
- `edition` 값 하나가 서버와 모든 클라이언트 이미지를 함께 바꾸므로, 차트가 판 세트 전환을 보장한다.
- 차트 버전·서명·values 스키마·Artifact Hub 페이지가 하나로 유지된다.
- 확장판 이미지는 엔터프라이즈 구독용이라 비공개 레지스트리에 두고 pull secret 을 요구한다. 확장판 values 는 고객에게만 준다.

### 착수 전 선행 조건 (고객 데이터가 생기기 전에)
세트 전환은 판이 섞이는 문제(아래 2)만 막는다. 1·3 은 판을 섞지 않아도 **확장판 자신이 다음 상류
버전 위로 옮겨 갈 때** 생기는 문제라 선행 수정이 필요하다.

1. **속성 번호.** `DAOS_PROP_CO_SPACE_LIMIT`, `SPACE_AMP`, `PROJ_QUOTA` 를 상류 열거형 끝(`PERF_DOMAIN` 다음)에
   이어 붙였다(`src/include/daos_prop.h`). 상류가 속성을 추가하면 같은 번호가 된다.
   → 상류와 겹치지 않는 번호대로 옮기거나, 속성 대신 컨테이너 사용자 속성(attribute)에 저장한다.
2. **CONT_QUERY 응답 구조.** `cqo_used`, `cqo_proj_used` 를 추가했지만 `DAOS_CONT_VERSION` 은 그대로다
   (`src/container/rpc.h`). 판이 섞이면 버전 검사를 통과한 채 형식이 어긋난다.
   → 사용량 조회는 새 RPC 로 내거나, 기존 RPC 를 바꾼다면 버전을 올린다.
3. **VOS 예약 영역.** 프로젝트 쿼터가 `vos_cont_ext_df.ced_padding1` 4칸을 썼다(`src/vos/vos_layout.h`,
   `VCEB_PROJ_TREE` 로 표시). 상류가 같은 자리를 쓰면 확장판 풀을 다음 버전으로 올릴 수 없다.
   → 상류와 자리를 맞추거나(상류 제안), 형식 버전을 올리고 이관 도구를 둔다.
4. exastor RPM(ac2repo stable 에 게시됨)이 쿼터 용도로 실제 쓰이는 곳이 있는지 확인한다. 있으면 1~3 의 이관 계획이 먼저다.

## 근거

## 결과와 트레이드오프
- 기본판만 쓰는 동안 CI·이미지·지원 범위가 한 벌로 유지된다. 쿼터·ACL 같은 POSIX 호환 기능은 제품에 없다.
- 두 판 운영을 시작하면 CI(이미지 빌드, e2e)가 두 줄이 되고, exastor RPM 을 이미지로 잇는 빌드 경로가 새로 필요하다
  (exa-build 는 RPM 빌드는 되지만 2.8 바이너리를 실행하지 못한다).
- 3.0 이식 비용이 가장 크다. 프로젝트 쿼터(+2,077줄)가 VOS 깊숙이 들어가 있어 3.0 에서 다시 짜야 할 수 있다.

## 재검토 조건
- 고객이나 PoC 가 쿼터·ACL 을 요구 조건으로 걸 때 → 4 를 다시 열고 선행 조건부터 처리한다.
- 상류가 쿼터·ACL 을 받아들이거나 비슷한 기능을 낼 때 → 확장판의 필요 자체를 다시 판단한다.
- DAOS 3.0 릴리스 시 → 기준선과 확장판 범위를 3.0 기준으로 다시 정한다.
