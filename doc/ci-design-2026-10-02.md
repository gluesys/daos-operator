# DAOS K8s CI 설계 — ExaCI5 슬롯 3·4 VM 클러스터 (2026-10-02)

허브의 [DAOS K8s 패키징 전체 테스트 CI 계획](https://ac2repo.gluesys.com/document-hub/?document=7b362953-1969-40b2-ba4f-fd5e5ac15110)
(`7b362953`) 과 [`ci-handoff-2026-10-02.md`](ci-handoff-2026-10-02.md) 를 바탕으로, 2026-10-02 에
확정한 **실제 구성**이다. 계획서는 "무엇을 테스트할 것인가" 를, 인수인계 문서는 "어떤 회귀를
잡을 것인가" 를 담고 있고, 이 문서는 **어디서 어떻게 돌릴 것인가** 를 정한다.

계획서와 달라진 점은 세 가지다. kind 를 쓰지 않는다. 실장비 대신 Proxmox VM 6대로 다중 노드
클러스터를 만든다. 스토리지 클래스 `nvme`·`kdev`·혼합을 모두 CI 가 검증한다.

## 3. 노드 준비

- **OS**: 6대 모두 `init` 스냅샷(Rocky 8.10, 커널 4.18)으로 되돌려 시작한다. da1~4 와 같은 커널이고
  CI 표준 자격증명이 살아 있다. Rocky 9 는 Tier 3 매트릭스 항목으로 미룬다.
- **K8s**: kubeadm, Kubernetes **v1.31.14**, CRI-O **1.31.5**(계획서 기준 버전). 컨트롤 플레인 4J,
  워커 4대 join. CNI 는 client-6 과 같은 것을 쓴다.
- **호스트 설정** (client-6 `/root/k8s-UNDO.md` 항목을 playbook 하나로 옮긴다): swap off,
  SELinux permissive, firewalld off, THP `never`, 2 MB hugepages **4096개(8 GB)** per 워커,
  `vm.nr_hugepages` 영구화, `uio_pci_generic` 모듈 로드.
- **이미지 사전 pull**: operator·hostprep·CSI·daos-images 6종·versitygw·vllm-lmcache 를 워커에
  pull 해 둔다. 스냅샷에 포함되므로 매 실행의 pull 시간이 없다.
- **3J**: gitlab-runner(shell executor), `registry:2` 컨테이너(airgap 테스트용), kubectl·helm·
  kubectl-daos, Ginkgo 실행용 Go 툴체인.

## 4. 스냅샷과 리셋 모델

클러스터 5대에 K8s 가 뜨고 이미지가 pull 된 상태로 스냅샷 **`k8s-ready`** 를 찍는다. zvol 은 ZFS
가 네이티브로 스냅샷하므로 `qm_ci` 의 raw 특수 처리가 필요 없고 `qm snapshot`/`qm rollback` 을
그대로 쓴다.

매 파이프라인 실행 전:

1. 3J 러너가 `ssh jenkins-ci@vdi5 sudo qm rollback <vmid> k8s-ready` 를 5대에 병렬로 보낸다
   (`jenkins-ci` 의 `qm`·`pvesh` NOPASSWD sudo 는 확인됨).
2. `qm start` 5대. 4J 의 API 응답과 워커 4대 `Ready` 를 기다린다. 목표 3분 이내.
3. 테스트 실행.

실측(2026-10-02): 롤백 → 5노드가 **롤백 이후 하트비트로** Ready 까지 **120초**. 처음 잰 46초는 틀렸다.
스냅샷 안의 etcd 가 롤백 직전의 Ready 를 그대로 돌려주기 때문에, `kubectl get nodes` 의 Ready 만 보면
kubelet 이 아직 안 뜬 노드도 Ready 로 센다. `rollback.sh` 는 `lastHeartbeatTime >= 롤백 시작` 인 노드만 센다.
GitLab 러너 경로 end-to-end: MR !2 파이프라인 59296 의 `env-reset` 잡(146214)이 3J 러너에서 롤백 126초, 5노드 Ready 로 성공(2026-10-02).

롤백이 DAOS 포맷 상태·NVMe 바인딩·finalizer 잔여물을 전부 지운다. 계획서가 요구한
"hostprep wipe", 인수인계가 제안한 "kubeadm reset 스크립트" 둘 다 필요 없다.

장애 주입: 노드 재부팅·노드 손실은 `qm stop/start` 로 실제로 일으킨다. 서버 pod·MS 리더·CSI
node plugin 재시작은 `kubectl delete pod` 로 한다.

## 5. 스토리지 프로파일

VM 에서 세 클래스를 모두 검증한다. 근거와 한계:

- QEMU NVMe 는 게스트에서 "QEMU NVM Express Controller" 로 보인다. FlexA daos_ci(34.21)가 같은
  장치를 `kdev` 로 쓰고 있고, 2026-09-15 테스트베드에서 hostprep 이 이를 `uio_pci_generic` 으로
  인식했다. **SPDK `nvme` 클래스로 서버를 띄운 선례는 아직 없다.** VM 에 vIOMMU 가 없으므로
  `spec.disableVFIO: true` 경로를 쓴다. 이 검증이 환경 구축의 첫 항목이다(10절 A-3).
  **2026-10-02 검증 결과: 성공(조건 2개).** exaci5-3a 에서 QEMU NVMe 2개를 `uio_pci_generic` 으로 묶어
  SPDK `nvme` 클래스로 포맷(402 ms), rank 0 join(targets 4), 8 GiB 풀 Ready 까지 확인했다. 현재 이미지 그대로는 안 되고
  아래 두 가지가 필요하다. 둘 다 운영 노드에도 해당하는 결함이다.
  ① daos-server·daos-hostprep 이미지에 **kmod 가 없다.** SPDK `setup.sh` 는 `lsmod`/`modprobe` 가 없으면 `set -e` 로
  바인딩 전에 조용히 끝나고, `daos_server nvme prepare` 는 성공으로 보고한다.
  ② 서버·hostprep 파드에 **호스트 `/lib/modules` 가 없다.** 모듈이 이미 로드돼 있어도 `modprobe uio_pci_generic` 이 실패한다.
  검증은 kmod 를 넣은 로컬 이미지와 `/lib/modules` 읽기 전용 hostPath 를 StatefulSet 에 직접 붙여 했다.
  부수 발견: (a) DaosSystem `spec.images.server` 를 바꿔도 operator 가 기존 StatefulSet 템플릿에 반영하지 않는다.
  (b) 포맷이 실패하면 operator 가 `format-approved` 어노테이션을 지운다. 재시도에는 재승인이 필요하다.
  **2026-10-03 재검증: 무패치 통과.** CI 가 빌드한 이미지(daos-images `2.8.0-20261003-g9927f7be`, operator·hostprep
  `bdb57d99`)만으로 `verify-nvme.sh` → `NVME_CLASS_OK`(롤백 121초, 두 장치 `uio_pci_generic`, rank 0 join, 8 GiB 풀 Ready).
  관찰 2건(Tier 1 스펙에 반영할 것): (c) 풀 생성 직후 DaosSystem 이 30초가량 `Ready=False RanksNotJoined 0/0`,
  `ManagementService=NoQuorum` 으로 내려갔다가 스스로 `Ready`/`Leader` 로 돌아왔다. 멤버십 조회 주기 사이의 일시적 표시로 보이며,
  `Ready` 를 한 번만 보고 판정하는 테스트는 흔들린다. (d) operator 가 첫 `dmg pool create` 가 끝나기 전에 두 번째 생성
  Job 을 띄워 `code 609 label already exists` 로 실패한 Job 이 남았다. 풀은 정상이다.
- 노드당 2엔진은 operator 가 `spec.engines[]` 로 렌더하고 fabric 포트를 엔진마다 100 씩 올린다.
  daos_ci 와 같은 구성이다.
- `spec.engines[].bdevTiers`(NVMe 에 wal·meta, kdev 에 data)는 CRD 주석대로 "출하 형태"인데
  CI 는 물론 수동 검증 기록도 없다.

| 프로파일 | 노드 | 엔진 구성 | fabric | 검증 포인트 | Tier |
|---|---|---|---|---|---|
| `nvme-1rank` | 3A | nvme class ×1, targets 4, `disableVFIO`, hostPrep `bindNvme=true` | tcp/`vmbr1` | 운영 유일 지원 클래스. hostprep 발견→annotation→bind→format. DSN 없는 장치 처리 | 1 |
| `kdev-3rank` | 3A·3B·4B | kdev ×1(`scsi1`), MS 복제본 3 | verbs/`ib0` | 다중 rank, MS 정족수, rank 재편입, drain, scale-out(4A) | 2 |
| `mixed-2engine` | 3A·3B·4B | engine0 nvme(`nvme0`), engine1 kdev(`scsi1`), 6 rank, `ib0` 공유, 포트 31316/31416 | verbs | 포트 오프셋, NUMA 핀, `dmg storage query usage` 패닉(혼합 bdev_list) xfail 고정 | 2 |
| `tiers` | 3A·3B·4B | 엔진당 nvme[wal,meta](`nvme0`) + kdev[data](`scsi1`,`scsi2`) | verbs | 역할 분리 렌더링과 포맷 | 2 |
| `gpu` | 4A | 클라이언트 전용. `kdev-3rank` 위에 vLLM+LMCache | verbs | warm-up, oclass 변경(rd_fac≥1) | 3 |

공통: `scm: ram` 4 GiB/엔진, `systemRamReservedGiB` 는 32 GB 노드에 맞게 명시(기본 64 는 기동
실패). 프로파일은 Helm values 파일 `test/e2e/profiles/<name>.yaml` 로 둔다.

## 6. CI 배선

**GitLab CI 로 통일**한다(계획서 4절). Jenkins 는 라벨 예약 외에 쓰지 않는다. 나중에 수동 실행용
Jenkins 잡이 필요하면 3J 의 에이전트가 받을 수 있다.

러너:

| 러너 | 위치 | executor | 태그 | 용도 |
|---|---|---|---|---|
| `ci-runner`(id 44, 기존) | ExaCI5-23J | docker, 동시 4 | `Flexa` | Tier 0 check 잡. 주당 약 1,800잡을 이미 처리 중 |
| exa-build(id 50, 기존) | exa-build | shell+podman | `daos-build` | 이미지 빌드·푸시. **DAOS 2.8 바이너리 실행 불가**(아래 12절) |
| **신규** | ExaCI5-3J | shell | `daos-k8s` | Tier 1~3. `resource_group: daos-k8s-ci` 로 클러스터를 한 파이프라인만 쓴다 |

자격증명은 GitLab CI 변수(masked, file 타입)로 넣는다: `KUBECONFIG`, 워커 SSH 키, vdi5
`jenkins-ci` SSH 키. `~/.docker/config.json`·`tokens/*` 평문 파일을 러너가 읽는 일은 없게 한다
(인수인계 3절 3항 종결).

저장소 간 트리거(계획서 4절): daos-images·daos-csi MR 은 operator 파이프라인을 `trigger` 로
호출하면서 자기 이미지 태그를 변수로 넘긴다. operator MR 은 각 저장소 `main` 최신 이미지를 쓴다.

Tier 2 는 스케줄 파이프라인(야간), Tier 3 은 주 1회 스케줄과 태그 파이프라인이다. 모두 `timeout`
을 명시한다(러너 다운 시 pending 누적 방지).

Tier 2 (야간, `kdev-3rank` → `mixed-2engine` → `tiers` 순):

- 각 프로파일에서 Tier 1 의 1~3·7 반복.
- rank 재편입: 서버 pod 삭제 → excluded → reintegrate → joined (인수인계, `0b9f544`).
- MS 정족수: 복제본 3 중 2 pod 삭제 → `ManagementService=NoQuorum` (인수인계 #34).
- MS 리더 kill: 제어 평면 10초 내 복구. 데이터 경로 약 2분 정지는 xfail + 소요 시간 기록.
- 노드 재부팅(`qm stop/start`) 후 pool 유지. 노드 drain/uncordon.
- CSI node plugin 재시작 후 staging bind 유지.
- 4A scale-out: 4번째 rank 포맷·join.
- `mixed-2engine` 에서 `dmg storage query usage` 패닉 xfail.
- 산출물: JUnit + 소요 시간 CSV(성능이 아니라 복구 시간 추이).

Tier 3 (주 1회·태그 전):

- chart 업그레이드 rc.3 → rc.4 → HEAD, 전후 데이터 검증.

- 매트릭스(선택): Rocky 9, containerd.

## 8. 머지 정책

계획서 6절 그대로. Tier 0·1 MR 차단, Tier 2 보고만, Tier 3 릴리스 태그 차단. 도입 초기 1~2주는
Tier 1 을 `allow_failure` 로 두고 안정되면 차단으로 바꾼다.

## 9. 이 구성이 못 보는 것

- 에뮬레이션 NVMe 의 **성능 수치는 의미가 없다.** 계획서의 기준치(verbs PVC 744 MB/s, dfuse
  587/914 MB/s)와 30% 임계치는 da1~4 야간 잡으로 남긴다.
- QEMU NVMe 에는 **DSN 이 없다.** 듀얼 포트 섀시 DSN 중복 검사(2026-09-03 사고)의 "중복 감지"
  쪽은 da1~4 에서 본다. "DSN 없는 장치를 거부하지 않는다" 쪽은 여기서 본다.
- 실 IB 스위치 장애, 노드 BMC 전원 제어는 없다.
